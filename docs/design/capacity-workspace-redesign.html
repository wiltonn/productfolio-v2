Capacity Workspace Redesign

The information architecture is right — Census, Capacity and Allocations are Engineering-wide. What is missing is a visual system and a way to change a number without reloading the page. This is what I propose to build, and what I need approved before writing application code.

01

What's there now

The application is about 2,300 lines of TypeScript run directly by tsx, with no build step and no runtime dependencies. Pages are template literals in src/web/views.ts; a single 49-rule STYLE constant is inlined into every <head>; every change is a <form method="post"> that writes through src/db/repo.ts and answers 303 back to the page it came from. The selected quarter and team ride in the query string (?q=1&team=2) and are rebuilt on every request. There is no client-side JavaScript at all, and no route that serves a stylesheet or a script.

That is a sound base. The domain layer is pure and well-tested, validation is on the server where it belongs, and test/workflow.test.ts already boots the real server on an ephemeral port and asserts against fetched HTML — so the interaction work has somewhere to be tested from day one.

What is actually wrong

F1
The tables are forms, not data

Census presents 58 input boxes and 42 buttons at once. Every person's overhead sits in a live text field with its own Set button; every schedule and absence form is a permanently visible disclosure. Reading "who is in Engineering and what is their capacity" means reading past the controls for changing it.

F2
A rejected value is thrown away

Entering an overhead of 250% replaces the entire page with a Could not save screen and a Go back link. The typed value is gone, the scroll position is gone, and the reader has to find the row again. Verified against the running app.

F3
Every save is a full page reload

Changing one number re-renders and re-fetches the whole page. Setting overhead for six people is six reloads, each losing focus and scroll. The figures that must update are only ever a few — the person's row, the team total, the capacity chain, the reconciliation — but the whole document is replaced to show them.

F4
Destructive actions are ordinary furniture

Twelve red Remove person and × buttons sit in the Census table with no confirmation step. Removing a person deletes their schedules and absences and logs a change that flags every feasibility judgment in that team-quarter for reassessment — with one click, at the same visual weight as a filter.

F5
Wide tables push the page sideways

The nine-column Census table has no scroll container. At a 1280px window the document is already 1293px wide, so the whole page — navigation included — scrolls horizontally. On a laptop screen it is worse, and there is no responsive treatment below that.

F6
The quarter selector is a form you must submit

Quarter and team are chosen in per-page Show and Filter forms inside a card. They are shared context for the whole workspace, not page content, and changing quarter should not be a two-step action repeated identically on three pages.

The content on these pages is good. The reconciliation identity is spelled out, denominators are stated, Beacon's shortfall is called out in words next to Atlas's headroom, and the reassessment reasons are listed. None of that needs rewriting — it needs a system that lets it be seen.

03

Can this stack do inline editing? Yes — and it should

No framework and no component library. I looked for a limitation that would justify one and did not find it. The pages are small, the forms are simple, the calculations must stay on the server anyway, and the whole interaction surface is: swap a read cell for an input, post it, put the server's answer back on the page. That is roughly 180 lines of vanilla JavaScript. React, htmx or Alpine would each add more to reason about than they remove, and every one of them costs the zero-dependency, no-build-step property the project chose deliberately.

What does need adding is small and additive:

  • Two new routes, /assets/app.css and /assets/app.js, serving string constants from src/web/assets.ts with a content hash in the filename. Existing page URLs are untouched.
  • Content negotiation on the existing POST routes. A request that sends Accept: application/json runs the same handler, the same repo call, the same validation — and gets JSON back instead of a 303.
  • Server-rendered fragments. The JSON carries re-rendered HTML for the regions whose figures moved, so the browser never computes a capacity figure.

Without JavaScript every editor is still a real form with a real submit button and the app behaves exactly as it does today. The enhancement is layered on top, not depended upon.

The save protocol

BrowserCell commits. It takes the next sequence number for that field key (overhead:person-1) and aborts any request still in flight for the same key.
BrowserPOST /people/1/overhead — the same URL and the same body the form posts today, plus Accept: application/json.
ServerSame handler, same repo.setOverhead(), same validation, same change-log rule. No new business logic.
ServerOn success: 200 with { ok, regions: { … }, status } — re-rendered HTML for the person row, the team total row, the capacity chain, the reconciliation and the planning-state counts.
ServerOn a rejected value: 422 with { ok:false, message } — the message the domain already produces, e.g. "Overhead percent must be between 0 and 100, got 250".
BrowserIf the response's sequence number is not the latest for that key, discard it. A slow older save can never overwrite a newer value.
BrowserOtherwise swap each returned region, restore focus by its stable key, and announce the result in one aria-live="polite" region.
BrowserOn failure the input keeps the typed value, the cell turns red with Retry and Discard, and a beforeunload guard blocks navigation while anything is dirty or in flight.

Why no optimistic figures

A pending cell shows the value you typed and a Saving… state. It never shows a recalculated capacity, reconciliation or feasibility state until the server sends one. Nothing unconfirmed is presented as final, and the browser holds no copy of the capacity arithmetic to get out of step with.

07

Kept separate from this work

A better editing surface asks for operations the application does not have. I am not adding business behaviour while doing visual work. These are listed so you can decide on them on their own merits — the redesign ships without any of them.

ItemWhat it isMy recommendation
Setting overhead erases its note
defect, found while auditing		 The Census overhead form has no note field, but the save writes note = '' unconditionally. Pressing Set on Lena — even to keep 40% — silently deletes "team lead: management & admin". Reproduced against the running app. Fix it, but as its own change: keep the stored note when the request carries none, and expose the note in an Edit overhead dialog. This alters persistence behaviour, so it needs your yes.
No way to edit a person A person's name, joined date and left date can only be set at creation. Correcting a typo or a start date means removing and re-adding them, which deletes their absences and logs two changes. Needed for the "effective-date operations" the brief asks for. A new operation — flagging, not building.
No way to edit a WorkPackage Only the estimate can be changed. Name, category and notes are fixed after acceptance. Recategorising moves engineer-weeks between investment categories, which is a planning decision with change-log consequences. New operation. Decide the change-log rule first.
Teams and quarters cannot be edited or removed No rename, no delete, no change to a quarter's dates. Changing quarter dates would recompute every capacity figure in it. New operations. Out of scope here.
Undo The change log only grows by design (D15): reverting a value is itself a change and must not revive a judgment. A true undo would have to be a forward compensating operation that restores deleted absences and schedules without resurrecting feasibility. Defer, as the brief says. Confirmation dialogs carry the weight instead.
Commitments and baselines Modelled in the domain but not implemented — deferred by D14. Unchanged. The redesign leaves room for them.

How it gets verified

npm test and npm run typecheck stay green throughout — the existing suite already asserts the X1, X6, X9 and X10 figures appear in the rendered HTML, which is exactly the regression net a visual rewrite needs. On top of that, new tests posting to the real server with Accept: application/json:

  • a successful save returns the recalculated regions, and the figures in them are right;
  • a rejected value returns 422 and the domain's own message, and writes nothing;
  • two rapid edits to the same field settle on the later value, whichever response lands first;
  • re-submitting an unchanged value adds no row to the change log;
  • an edit that invalidates a judgment comes back with that judgment flagged for reassessment;
  • quarter and team survive an edit, and the response is scoped to the right team-quarter;
  • Beacon's 2.9 ew shortfall stays visible while the view is filtered to Atlas.

Keyboard operation, narrow screens and the before/after screenshots are checked by driving the running app, not by reading the source. All of it lands on a feature branch as a draft PR.
